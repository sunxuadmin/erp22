# CREHN Codex 协作开发流程 V1.1

## 1. 状态闸门

```text
ANALYZE
  → CONFIRMED
  → IMPLEMENTING
  → IMPLEMENTED
  → VERIFIED
  → COMMIT_APPROVED
  → DEPLOY_APPROVED
```

- `ANALYZE`：只读检查需求、代码、数据、配置和风险；
- `CONFIRMED`：用户明确确认实现方案和边界；
- `IMPLEMENTING`：仅实施已确认范围；
- `IMPLEMENTED`：代码或文档已完成但不等于验证通过；
- `VERIFIED`：完成与风险相称的静态、单元、集成、浏览器或服务端验证；
- `COMMIT_APPROVED`：用户明确授权本地 Git 提交；
- `DEPLOY_APPROVED`：用户明确授权部署、执行 SQL/迁移或其他外部变更。

任何前一阶段的确认都不自动授权后一阶段。用户说“先分析”“先确认后再改”时，必须停留在只读阶段。

## 2. 分析模板

实施前至少回答：

1. 需求目标、角色和完整业务流程是什么；
2. 影响哪些模块、页面、接口、表、文件和配置；
3. 权限、数据范围、状态机、版本快照和兼容性如何变化；
4. 是否触及 DYZ、生产环境、数据库或存储；
5. 可选方案、推荐方案和取舍；
6. 验收方法、风险、回滚和明确不做项。

不清楚但可从文档或代码发现的信息先查证；会实质改变业务结果的选择交由用户确认。

## 3. 实施规范

- 实施必须遵守 [工程规范中的最小改动与禁止推测性开发](../02-工程规范/CREHN_PROJECT_RULE.md#3-最小改动与禁止推测性开发)，不得用“顺便优化”扩大范围。
- 开始前读取当前目录的 `AGENTS.md`、`TASKS.md`、`PITFALLS.md` 等约束（若存在）。
- 先检查工作区状态，保留用户和其他任务的并行修改。
- 修改前检索已有实现、组件、工具类、DTO、枚举、接口和配置；确认可复用项、写入所有者和唯一规则来源后再编辑。
- 按一个业务边界实施，可拆成多个原子提交；“一个任务只能一个提交”不是强制规则。
- 前端按钮、后端权限、数据范围、状态机、数据库约束和审计同步考虑。
- 复用 RuoYi-Vue-Plus 和项目共享组件，不复制 DYZ 冗余实现。
- DYZ 兼容差异集中在适配器，不渗入核心领域代码。
- 新增文件、依赖、环境变量、配置、接口、数据库字段或公共模块前，必须确认现有结构无法承载且需求已经授权。
- 发现歧义时采用最小影响解释；若会改变业务流程、数据、权限、兼容范围或验收结果，停止实现并请求确认。
- 修改文档时明确“规范已更新”与“功能已实现”的区别。

## 4. 验证证据

每项检查标记：

- `PASS`：已运行并通过；
- `FAIL`：已运行未通过；
- `NOT_RUN`：未运行并说明原因；
- `NEEDS_BROWSER`：需要登录浏览器/真实交互；
- `NEEDS_SERVER`：需要后端、数据库、存储或部署环境。

构建通过不代表权限、数据隔离、文件授权或生产部署通过。保存成功提示不代表数据持久化，需回读服务端值。

## 5. Git 边界

- 提交前审查 `git status`、差异、未跟踪文件、敏感信息和测试结果；
- 仅暂存当前业务边界文件，禁止无差别提交并行改动；
- 提交信息用清晰中文说明业务目的、主要变化和验证；
- 本地提交、推送、创建 PR、合并、部署分别需要相应授权；
- 未获授权不得重置、清理或覆盖用户已有改动。

## 6. 数据库与部署

- 方案确认不是执行 SQL、导入数据、清库或部署的授权；
- 先提供 dry-run/清单/影响统计和回滚方案，高风险 Apply 前再次确认；
- 部署前核对产物、配置、SQL manifest、目标环境、备份和当前并行工作；
- 部署后验证健康、版本、关键 API 和回读，失败按预案回滚。

## 7. 任务交付

交付说明必须包含：

- 已完成内容和明确未做内容；
- 实际修改文件，以及每个文件修改的原因；
- 是否新增依赖、环境变量、配置项、公共模块、接口、数据库字段或迁移 SQL；
- 已运行的测试、检查、浏览器或服务端验证及其结果；
- 尚未处理的风险、未验证项和环境限制；
- Git、数据库、部署及外部系统的实际处理状态；
- 下一步需要用户确认的事项。
