# CREHN 工程规范

## 1. 架构决策

- 采用 RuoYi-Vue-Plus 模块化单体，不在 V1 引入微服务。
- CREHN 独立仓库、数据库、Redis 命名空间、对象存储前缀、配置、租户和部署产物。
- 艺术赛事业务放入独立业务模块，不写入 RuoYi 系统模块。
- 公共门户与管理端可分别构建和部署，但共用稳定业务 API 和资源权限模型。
- DYZ 兼容通过适配器模块实现，核心领域不得依赖 DYZ 实体和数据库表。

## 2. 初始技术基线

CREHN 初始化时以当前已检查 DYZ 技术栈为基线：

- RuoYi-Vue-Plus `5.6.1`
- Java `17`
- Spring Boot `3.5.14`
- MyBatis-Plus `3.5.16`
- Vue `3.5.30`
- TypeScript `5.9.x`
- Vite `7.3.x`
- Element Plus `2.13.x`
- Pinia `3.0.x`

项目创建后以 CREHN 锁文件和版本清单为权威来源。后续升级单独评估，不要求与 DYZ 永久同步升级。

## 3. 最小改动与禁止推测性开发

本项目执行“最小改动、明确职责、禁止推测性开发”原则。最终目标是实现当前已确认需求，不追求过度通用，不提前设计未知需求，不通过兜底代码掩盖问题。

开发时必须遵守：

1. 只修改当前需求直接涉及的代码，不重构无关模块，不批量格式化无关文件。
2. 修改前先全局检索现有实现、组件、工具类、DTO、枚举、接口和配置，优先复用，禁止重复创建相似功能。全局检索用于定位候选实现，确认目标后应收窄到相关模块。
3. 禁止添加没有明确需求依据的兜底逻辑、兼容分支、降级逻辑、预留字段、扩展接口和抽象层。已经确认的 DYZ 兼容需求仍须对应明确协议、版本或验收用例，不能演变为无限兼容。
4. 不得使用空 `catch`、静默失败、固定成功返回、假数据、空对象或默认值掩盖真实错误。
5. 必要的参数校验、权限校验、事务回滚、超时处理和边界检查必须保留，但只能放在职责明确的层级。
6. 不为单一实现创建接口、策略、工厂、处理器或只有一行转发代码的中间层。只有存在明确替换点、多个真实实现或框架契约时才引入对应抽象。
7. 同一业务规则只能保留一个权威实现，禁止在前端、Controller、Service、Mapper 中重复复制业务逻辑。前端可以提供同规则的交互提示，但服务端权威校验必须唯一。
8. 未经明确说明不得新增第三方依赖、环境变量、数据库字段、配置项或公共模块。
9. 禁止硬编码服务器地址、路径、角色 ID、用户 ID、活动 ID、密码、密钥和业务状态数字。
10. 数据库变更必须提供迁移 SQL，并评估历史数据、索引、唯一约束、事务和回滚风险。
11. 禁止为了通过编译而使用 `any`、忽略警告、删除测试、注释代码、放宽权限或返回固定结果。
12. 不新增无明确用途的 README、总结文档、临时脚本和重复测试文件。
13. 优先修改现有代码；只有现有结构无法合理承载需求时才新增文件，并在交付说明中解释新增原因。
14. 每个新增类和函数必须具有明确职责，命名必须体现具体业务含义，禁止使用 `Common`、`Helper`、`Manager` 等无法说明业务职责的模糊命名。
15. 发现需求存在歧义时，不得自行扩展需求；对于不改变业务结果和授权边界的细节，选择影响范围最小且符合现有规则的实现，并在结果中说明假设。若歧义会改变业务流程、数据、权限、兼容范围或验收结果，必须先确认。

每次交付必须列出：

- 修改了哪些文件；
- 每个文件修改的原因；
- 是否新增依赖、配置、接口或数据库变更；
- 执行了哪些测试或检查及其结果；
- 尚未处理的风险和未验证项。

## 4. 模块化和职责

- 一个业务能力只有一个写入所有者。
- Controller 只负责协议、鉴权入口、参数校验和响应。
- 应用 Service 负责编排事务和状态转换。
- 领域策略负责规则计算，不访问 HTTP 或前端状态。
- 查询服务可组合跨域只读数据，但不能越权修改其他模块表。
- 公共组件必须稳定、无业务歧义；不能建立万能 Service、万能 JSON 或万能弹窗。

## 5. 配置与代码常量

禁止硬编码：

- 活动名称、届次、时间、学校、名额、奖项比例、提示文字和文件限制；
- 生产地址、密钥、bucket、数据库和环境凭据；
- DYZ 数字 ID、角色 ID、菜单 ID 和 OSS ID。

允许并要求使用代码常量或枚举：

- 状态码、动作码、协议类型、权限标识；
- 稳定字段类型、文件状态和导入模式；
- 安全上限和不可绕过的业务不变量。

## 6. Rule Engine 边界

V1 使用类型化规则对象、校验器和策略注册表。活动配置可以选择策略并提供受限参数，但不得执行任意 JavaScript、SQL、SpEL、Groovy 或上传脚本。

新增规则必须说明：

- 配置结构和版本；
- 默认值和允许范围；
- 服务端校验器；
- 历史版本解释方式；
- 前后端共同支持情况；
- DYZ 兼容映射。

## 7. API 和错误

- 当前业务接口统一使用 `/crehn/<module>`，由 Web 层通过 `/prod-api/` 反向代理；如未来引入 API 大版本，须以独立需求和迁移方案调整，不能只改前端路径。
- 权限标识采用稳定结构，例如 `crehn:<module>:<action>`。
- 所有列表和导出使用同一数据范围规范。
- 批量操作返回逐项结果，不能只返回“成功”掩盖部分失败。
- 冲突、状态错误、校验失败、无权限和资源不存在使用可区分错误码。
- 幂等操作接受幂等键或使用业务唯一约束。

## 8. 数据和事务

- 跨多个核心表的状态转换在一个明确事务中完成。
- 外部文件上传、异步转换和通知使用可恢复状态，不假定远程调用与数据库事务原子一致。
- 更新使用乐观锁、唯一约束或行锁防止重复提交和并发签名。
- 历史快照只追加，不原地覆盖。

## 9. 质量约束

- 后端至少包含状态门禁、权限、数据范围、规则和兼容导入测试。
- 前端至少包含动态配置归一化、关键交互和窄屏布局测试。
- 跨端功能必须执行接口契约检查；只通过前端 lint 不能证明后端有效。
- 配置保存后必须服务端回读比较，不能只依赖成功提示。
- 兼容功能使用固定 DYZ 样例包执行契约测试。

## 10. Git 和授权

- 一个业务边界可以拆分为一个或多个可审查的原子提交，不强制一个任务只有一个提交。
- 修改前检查已有变更和并行任务，禁止覆盖无关文件。
- Git 提交、推送、数据库执行和部署均为独立授权。
- 未运行的验证明确记录为 `NOT_RUN` 或 `NOT_VERIFIED`。
