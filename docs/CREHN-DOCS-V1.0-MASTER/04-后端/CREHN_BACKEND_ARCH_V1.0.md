# CREHN 后端架构规范 V1.1

## 1. 技术基线

- 采用与 DYZ 同源的 RuoYi-Vue-Plus 技术栈，建立完全独立的 CREHN 服务、数据库、缓存、对象存储和配置。
- 业务形态采用“模块化单体”，先保证边界清楚，不在 V1 阶段引入微服务拆分成本。
- 复用框架已有的认证、RBAC、部门、字典、参数、日志、定时任务、消息、对象存储和 Excel 能力。
- 活动业务状态机由领域服务显式实现，V1 不引入通用 BPM 工作流引擎。

## 2. 业务模块

| 模块 | 职责 |
| --- | --- |
| identity-org | 用户、角色、单位、参赛者激活、账号安全 |
| competition-activity | 赛事、届次、活动、阶段时间、开放范围 |
| activity-config | 类别、字段、成员表、附件、评分、工作台配置 |
| registration-project | 报名、作品、成员、指导教师、附件、草稿与提交 |
| school-submit | 学校审核、推荐、退回、统一提交、批次锁定 |
| project-audit | 形式审核、内容审核、退回补正、审核日志 |
| review | 专家分配、匿名材料、评分、复核、签名表与锁定 |
| result | 评分汇总、异常处理、获奖结果、发布版本与撤回 |
| file | 上传、扫描、预览、授权下载、回收与清理 |
| cms | 栏目、文章、媒体、首页组件、发布与回滚 |
| theme-workbench | 门户主题、角色工作台、页面/组件注册、表格与文案配置、版本发布和回滚 |
| compatibility | DYZ 包解析、校验、映射、资源迁移和报告 |
| notification-export-audit | 通知、导入导出、异步任务、审计日志 |

模块之间只能通过应用服务、领域接口或只读查询接口协作，禁止跨模块直接修改他人业务表。

## 3. 分层与事务

```text
Controller/API
    ↓
Application Service（用例、权限、事务编排）
    ↓
Domain Service / Rule（状态、规则、快照）
    ↓
Repository / Mapper
```

- Controller 只做参数接收、协议转换和响应，不承载业务判断。
- 写操作以一个业务动作作为事务边界；文件上传、预览转换、通知和大批量导入使用任务状态协调，不依赖跨资源长事务。
- 状态迁移必须使用条件更新或乐观锁，冲突时返回当前状态和可执行动作。
- 规则引擎只负责字段、附件、成员、评分等可配置规则，不代替权限、状态机和数据一致性。

## 4. API 契约

- 当前 CREHN 业务 Controller 路径统一使用 `/crehn/<module>/...`；管理端和公共门户在浏览器侧通过 `/prod-api/` 反向代理访问，代理转发后仍是 `/crehn/...`。如未来引入 `/api/v1` 等 API 大版本，必须建立独立需求、兼容窗口和迁移方案，不能只修改前端路径；兼容导入协议继续使用独立的 `formatVersion`。
- 分页、排序、错误码、时间、金额/分数精度、文件引用采用统一格式。
- 写接口支持 `requestId` 或业务幂等键；重复提交不得生成重复项目、批次、评分或结果版本。
- 保存后返回服务端规范化结果或提供立即回读接口。前端成功提示不能代替回读。
- 列表接口只返回当前角色和数据范围允许的数据；字段脱敏和附件可见性由服务端裁定。
- 导入、导出、预览、汇总等长任务返回任务编号、进度、结果和失败明细。
- 页面配置的预览、保存和发布接口必须服务端校验 `page_key`、`component_key`、组件兼容组、字段/列、`action_key`、配置协议版本和目标作用域，不能信任前端生成的 JSON。

## 5. 服务端授权

每次敏感请求必须同时校验：

1. 登录身份是否有效；
2. 是否拥有功能权限；
3. 是否处于允许的数据范围；
4. 当前业务状态是否允许该动作。

前端菜单、路由和按钮仅用于体验，不是授权边界。单位管理员、审核员、评分员和汇总员不得通过修改请求参数越权访问其他单位、未分配项目或未授权结果。

页面与组件注册信息必须声明适用角色、必要功能权限、允许动作和数据契约。管理员向目标角色配置组件时，服务端返回缺失权限清单；缺失项可以保存在明确标记的草稿中，但发布必须拒绝并返回稳定错误码和缺口明细。配置服务不得写入角色权限关系，也不得提供“添加组件即授权”的旁路。

运行时仍以当前登录用户的实时权限和数据范围为准。已发布组件所需权限后来被撤销时，服务端不得返回组件数据或动作，前端按注册的安全降级规则隐藏或显示无权限占位，并将“发布配置与当前权限不一致”纳入可审计检查；历史发布快照不得因此被改写。

具体边界见 [角色与数据范围](../01-产品设计/CREHN_ROLE_DATA_SCOPE.md)。

## 6. 版本和快照

- 活动草稿配置可以修改，发布后生成不可变版本。
- 项目提交、学校统一提交、评分任务、签名评分表和结果发布都引用明确版本或快照。
- 历史数据必须按历史快照渲染，不能直接套用当前字段配置。
- 规则变更需区分“仅影响新数据”和“需要迁移历史数据”，后者必须走迁移发布流程。

## 7. 异步任务

适用场景：批量导入、批量激活码、文件扫描、媒体转码、预览生成、Excel/PDF 导出、专家分配、结果计算、兼容包迁移。

任务至少记录：类型、发起人、活动、状态、进度、输入摘要、输出文件、错误明细、重试次数、开始/结束时间。重试必须幂等，失败不能留下“半完成”业务状态。

## 8. 日志与审计

- 登录日志、操作日志和业务审计日志分层保存。
- 业务审计记录动作前后状态、操作者、角色、单位、对象、原因、请求编号、时间和必要差异。
- 评分修改、签名锁定、结果发布/撤回、权限变更、账号接管、文件删除、兼容导入必须可追溯。
- 审计日志不得记录密码、激活码明文、完整证件号、文件临时签名地址等秘密信息。

## 9. 明确禁止

- 禁止 CREHN 与 DYZ 共享业务数据库表、Redis key 空间、OSS bucket 凭据或运行时配置。
- 禁止以 JSON 字段绕开应由关系约束保证的唯一性和引用完整性。
- 禁止通过 SQL 直接改业务状态作为正常操作路径。
- 禁止将“评分汇总”直接等同于“最终结果发布”。
- 禁止在兼容层散落 DYZ 特例；所有差异集中在版本适配器与映射表。
