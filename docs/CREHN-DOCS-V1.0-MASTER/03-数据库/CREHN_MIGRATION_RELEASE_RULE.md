# CREHN 数据库迁移与发布规范

## 1. 迁移分类

| 分类 | 内容 | 自动执行 |
|---|---|---|
| `RequiredSchema` | 新表、兼容新增列、索引、约束 | 可在严格校验和备份后执行 |
| `ProgramMigration` | 菜单、权限、字典和程序默认配置 | 仅白名单幂等迁移 |
| `RuntimeConfig` | 活动、模板、页面和规则配置 | 不随普通部署自动覆盖 |
| `BusinessData` | 学校、账号、作品、评分、结果 | 仅专用导入/迁移任务 |
| `Seed/Test` | 演示和测试数据 | 禁止进入生产 |

## 2. 迁移文件要求

每个迁移必须记录：

- 唯一编号和文件路径；
- 目的和影响对象；
- 分类；
- 前置版本；
- 是否幂等；
- 锁表和数据量风险；
- 回滚或前向修复方案；
- 验证 SQL；
- 是否允许生产自动执行。

已执行迁移的路径和 SHA-256 写入迁移历史。相同路径内容发生变化时必须阻断。

## 3. 结构迁移约束

- 优先使用向后兼容的新增表、列和索引。
- 删除、重命名、类型收窄和大表回填必须拆分阶段。
- 应用发布前后存在兼容窗口时，旧版和新版都应能读取过渡结构。
- DDL 和大批量数据回填不得混在一个不可控事务中。
- 新约束先进行数据预检，再启用约束。

## 4. 配置和业务数据

- 活动配置、类别、字段、附件、角色工作台和门户内容不能放入普通结构 SQL。
- 业务配置通过版本化导入或管理员操作写入，并保留差异预览和审计。
- DYZ 历史数据使用专用导入批次，禁止用普通部署脚本覆盖 CREHN 数据库。
- 测试和演示数据仅进入明确测试环境。

## 5. 发布门禁

发布前：

1. 确认目标环境和组件范围；
2. 盘点代码、迁移、配置和资源变化；
3. 备份数据库和待替换产物；
4. 预演迁移清单；
5. 执行结构兼容检查；
6. 在测试环境运行升级和回滚验证。

发布后：

1. 检查应用、数据库、缓存、对象存储和异步任务健康；
2. 实际访问登录、门户和关键 API；
3. 回读迁移历史和关键结构；
4. 校验服务端产物指纹；
5. 执行最小业务链路；
6. 保存发布证据和回滚点。

## 6. 回滚

- 应用产物回滚不自动回滚数据库。
- 兼容新增结构通常保留，通过应用回滚恢复服务。
- 破坏性迁移必须有数据库备份和演练过的恢复步骤。
- 已写入的新业务数据优先使用前向修复，禁止无分析直接恢复旧库覆盖。
- 对象存储、工作台资源和门户资源分别纳入备份清单，不能假定数据库备份包含文件。

## 7. 禁止

- 普通部署自动执行完整活动配置快照；
- 未分类 SQL 进入生产清单；
- 修改已执行迁移文件；
- 在生产服务器临时构建未验证源码；
- 不备份就执行结构或业务数据迁移；
- 把 DYZ 数据库 dump 当作 CREHN 常规升级脚本；
- 只凭 HTTP 200 判断新版本已经生效。

## 8. 不可变产物晋级

1. 192.168.2.229 从明确提交构建后端、管理端、门户和 Docker 镜像；
2. 执行测试、Compose解析、迁移预演和健康检查；
3. 保存提交号、镜像版本/摘要、文件 SHA-256、迁移清单和测试报告；
4. 经人工发布批准并核验主机指纹后，将同一镜像归档传输到专用 ECS 2；
5. 生产先备份，再校验摘要、预演迁移、执行允许的迁移并切换镜像；
6. 发布后分别验证内部服务、反向代理、公开入口、文件和持久化回读。

初期使用 `docker save` 产生镜像归档并计算 SHA-256；私有 Registry 需要单独需求和安全评估。日常发布不复制数据库、Redis、对象存储、环境密钥或容器数据卷。

数据库首次初始化和后续迁移使用同一独立入口但不同操作类型。首次初始化只允许空业务库且写入完成标记；后续迁移必须先提供已审查的编号、分类、SHA-256、影响、备份、回滚/前向修复和验证 SQL，现有初始化清单不得被当作日常升级脚本重复执行。
