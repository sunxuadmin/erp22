# CREHN AI 开发上下文

## 1. 项目定位

CREHN 是面向全省高校的艺术设计赛事平台，包含独立公共门户和按角色进入的业务管理端。

核心业务链：

`学校及账号准备 → 参赛者本人激活 → 本人填报 → 学校审核推荐 → 学校最终批次提交 → 省级形式审查 → 专家评审 → 评分汇总 → 结果生成 → 结果发布`

## 2. 已确认的固定决定

- CREHN 使用与 DYZ 相同的 RuoYi-Vue-Plus 技术栈，但重新建立独立项目。
- CREHN 不在 DYZ 目录中继续开发，不共享 DYZ 数据库、对象存储或部署配置。
- 公共门户为独立门户，支持文章、媒体、栏目和组件化首页。
- 报名默认从 `2026-09-01 00:00` 开放，必须可由活动管理员调整。
- 默认面向全部学校，学校清单由 CREHN 单独维护；同时保留未来切换指定学校范围的能力。
- 参赛者必须拥有本人账号并本人填报。学校联络员批量导入名单或生成一次性激活码，参赛者本人激活并设置密码，省级管理员兜底。
- 当前“艺术与科技”等通知修订内容按最终稿处理。
- CREHN 将来兼容 DYZ 活动，但通过版本化活动包和适配器迁移，不采用共库或实时双写。

## 3. AI 与开发人员的硬性工作原则

1. 先分析影响范围、业务规则、数据变化、API、页面、权限和风险，再等待确认。
2. 未确认前保持只读；文档确认不自动授权代码、数据库、Git、部署或外部提交。
3. 采用模块化单体，优先使用 RuoYi-Vue-Plus 已有安全、用户、Excel、OSS、日志和字典能力。
4. 活动差异采用配置；身份、数据隔离、状态合法性、评分锁定和结果发布等硬约束必须由服务端代码保证。
5. 发布后使用历史快照；禁止让后续配置修改重解释已经提交、签名或发布的数据。
6. 所有危险状态变化、批量导入、评分调整、结果生成与发布必须可审计。
7. 不直接复制 DYZ 冗余实现；先提炼职责、稳定编码和兼容映射。
8. 所有完成结论必须附验证证据，未验证项明确写为 `NOT_VERIFIED`。
9. 执行最小改动、明确职责和禁止推测性开发；修改前检索复用，禁止顺带重构、过度抽象和提前设计未知需求。
10. 不使用空 `catch`、静默失败、固定成功、假数据、空对象或默认值掩盖真实错误。

## 4. 禁止行为

- 不以隐藏前端按钮代替后端权限和数据范围校验。
- 不把 DYZ 的数据库表、实体类或数字 ID 作为 CREHN 的对外兼容协议。
- 不静默覆盖导入目标，不静默丢弃未知字段或资源。
- 不修改已发布结果、已签评分表和历史提交快照。
- 不把业务运行配置、测试种子或历史数据混入普通结构迁移。
- 不因“配置化”引入可执行任意脚本或不受控表达式。
- 不为通过编译而使用 `any`、忽略警告、删除测试、注释问题代码、放宽权限或返回固定结果。
- 未获明确授权不新增第三方依赖、环境变量、数据库字段、配置项、接口或公共模块。

详细执行规则以 [CREHN 工程规范](../02-工程规范/CREHN_PROJECT_RULE.md#3-最小改动与禁止推测性开发) 为唯一权威来源。
