# CREHN 长期技术与治理决策

> 只记录会影响后续开发、迁移、权限或发布的决定。普通实现细节仍留在任务卡和代码中。

## 已确认决策

### D-001 CREHN 与 DYZ 完全隔离

- **决策**：CREHN 使用同源技术栈独立实现；DYZ 只作为功能参考和兼容输入。
- **原因**：避免跨系统耦合、主键/权限/配置污染和生产风险。
- **影响**：源码、数据库、对象存储、密钥、配置、运行标识和部署路径全部独立。
- **不采用**：共库、双写、复制 DYZ 数字主键、直接复用生产配置。
- **以后修改**：原则上不允许。若需互操作，只能经版本化导入导出/适配器、样例和回滚评审。

### D-002 模块化单体与独立公共门户

- **决策**：后端保持 RuoYi-Vue-Plus 模块化单体；管理端和公共门户独立构建，门户通过受控 CMS/公开接口读取数据。
- **原因**：复用成熟基础设施，同时隔离公共访问面和管理面。
- **影响**：业务代码归 `ruoyi-crehn`，公共页面不直接复用管理端权限上下文。
- **不采用**：当前阶段拆成微服务；让门户直连数据库或私有管理接口。
- **以后修改**：只有出现明确容量/组织边界并完成 ADR、迁移和回滚设计后允许。

### D-003 参赛者本人填报，学校审核和最终提交

- **决策**：学校负责名单、一次性激活码、审核/推荐和最终批次提交；参赛者本人激活正式账号并填报作品。
- **原因**：身份真实性、责任边界、审计和隐私要求。
- **影响**：权限、页面、服务和状态机必须禁止学校静默代填；当前实现冲突由 `FLOW-001` 修正。
- **不采用**：学校直接创建并以参赛者名义正式提交。
- **以后修改**：仅在产品、法务/审计规则明确变更，并完成权限与历史数据迁移评审后允许。

### D-004 四层授权模型

- **决策**：授权同时检查功能权限、角色身份、业务数据范围和业务状态。
- **原因**：菜单可见性或单一权限字符串不能保护跨学校、跨专家和不可变状态数据。
- **影响**：前端隐藏只能改善体验；所有写接口必须服务端校验并记录审计。
- **不采用**：只依赖前端按钮、只依赖角色名、结果模块通配授权。
- **以后修改**：只能收紧或在完整威胁/回归评审后扩展。

### D-005 稳定业务键优先于数字主键

- **决策**：跨环境、配置、导入导出和兼容契约使用稳定 code/key；数字主键只作库内引用。
- **原因**：不同环境的自增 ID 不稳定。
- **影响**：工作台使用 `role_key`，配置包使用活动/类别/字段/组件等稳定键。
- **不采用**：把活动 ID、角色 ID、页面 ID 固化到可迁移 JSON 或前端长期配置。
- **以后修改**：不允许倒退；新增稳定键必须有唯一性、版本和迁移方案。

### D-006 受控配置与分层继承

- **决策**：UI 配置按“系统→活动→角色→页面→类别”继承，只允许白名单组件、令牌、字段和数据源。
- **原因**：需要可配置性，同时保持权限、安全、可测试和兼容边界。
- **影响**：禁止任意 CSS/JS/HTML/SQL/iframe；发布时生成不可变快照并保留旧版本读取能力。
- **不采用**：低代码任意脚本、前端直接保存不受控执行片段。
- **以后修改**：新增配置键必须有默认值、校验、兼容版本和回退行为。

### D-007 不可变业务快照

- **决策**：已提交批次、已签名评分表和已发布结果版本不可原地修改。
- **原因**：审计、签名、争议处理和发布一致性。
- **影响**：纠错创建新版本/新流程并保留审计；配置变化不回写历史快照。
- **不采用**：管理员直接覆盖已签名或已发布数据。
- **以后修改**：原则上不允许；法定纠错必须有独立流程和完整留痕。

### D-008 环境隔离与不可变产物晋级

- **决策**：LOCAL、TEST、STAGE、PROD 严格隔离；PROD 只部署通过 TEST 验证的同一不可变镜像/前端资产。
- **原因**：消除生产现场构建和环境漂移。
- **影响**：数据库操作、部署、服务器连接和 Git 推送分别授权；PROD 不从源码构建。
- **不采用**：跨环境共库、浮动标签、在生产主机临时编译。
- **以后修改**：仅通过正式 ADR、供应链和回滚审查。

### D-009 数据库执行实行清单、备份、隔离恢复和显式授权门禁

- **决策**：任何 TEST/PROD 初始化或迁移前必须核对清单、生成计划、备份、完成可恢复性证据，并单独取得 SQL 授权。
- **原因**：逻辑备份成功不等于可恢复，且历史 SQL 存在模板/正式业务/冲突项混合。
- **影响**：V005/V006 文件存在不代表已执行；不能用代码实现授权推导数据库授权。
- **不采用**：直接全量运行历史 SQL、在目标库试错、把备份文件存在当作恢复验收。
- **以后修改**：门禁不得降低；自动化只能增加可审计性。

### D-010 消息渠道初期仅启用站内消息

- **决策**：短信、邮件在真实供应商和安全配置完成前关闭。
- **原因**：避免虚假发送状态、密钥和费用风险。
- **影响**：业务通知必须能在站内消息完成，外部渠道是后续显式能力。
- **不采用**：用占位配置假装发送成功。
- **以后修改**：需供应商、密钥管理、模板、失败重试、审计和成本授权齐备。

### D-011 Git 与发布授权分离

- **决策**：分支模型为 `main + feature/REQ-* + 发布标签`，不设长期 `develop`；`origin` 保持本地 Synology 裸仓库，GitHub 为独立远端。
- **原因**：保持简单可追踪，并保留本地备份所有权。
- **影响**：提交、向任一远端推送、打标签和部署均逐次授权。
- **不采用**：用 GitHub 覆盖既有 `origin`；把实现授权视为提交/推送授权。
- **以后修改**：需明确迁移计划和远端备份验证。

### D-012 三个长期顶层会话

- **决策**：长期只保留 `00-项目总控调度`、`10-集成联调`、`90-审查与发布`；普通开发使用总控分配的子代理。
- **原因**：减少重复总控、会话漂移和未沉淀结论。
- **影响**：子代理结果必须回写任务卡或 `HANDOFF.md`，任务状态统一在 `TASK_BOARD.md`。
- **不采用**：每个功能创建长期顶层会话；多个会话各自维护项目总清单。
- **以后修改**：只有长期独立产品线且现有三会话无法承载时，经总控记录原因后增加。
